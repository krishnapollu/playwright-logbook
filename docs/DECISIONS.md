| 2026-09-30 | How broad should the real-Playwright fixture be? | Use a bounded behavior matrix with a dedicated UI/API fixture, not every Cartesian product | Installed Playwright 1.63.0 reports `trace` as `application/zip` on retry 1 with `on-first-retry`; failed first attempts supply screenshot (`image/png`), video (`video/webm`) and `error-context` (`text/markdown`). Expected-fail has `expectedStatus: failed`, a failed attempt and `outcome: expected`. Stable outcomes/attachment placement are asserted; binary artifacts and durations are not. See `docs/PLAYWRIGHT-MATRIX.md`. |
| 2026-09-30 | Which Monocart ideas fit v3? | Prioritize trustworthy trace/attachment UX and allow-listed annotations; defer telemetry, coverage and external integrations; reject executable/report-HTML customization | The upstream README describes these features, but Logbook's offline and AI-debugging focus makes evidence quality and explicit consent more valuable than widget parity. See `docs/REPORTER-COMPARISON.md`. |
| 2026-09-30 | How should v3 protect run IDs without breaking explicit re-merge? | Atomically hard-link completed temporary JSON for ordinary shard/run writes; identical replay is a no-op, different content conflicts. Keep `logbook merge` an explicit replacement operation. | The read-only golden test re-merges a previously complete run after removing a shard, so a blanket ban on replacement would break an existing workflow. The reporter's default write path is guarded, never throws or changes Playwright's exit code, and warns on conflict. |
| 2026-09-30 | How should reports handle missing artifacts? | Resolve path availability during reporter/CLI model construction; suppress links for known-missing or escaping files, label unknown links unverified, and identify traces by verified name plus ZIP content type. | `renderReport` stays pure and offline. No trace ZIP bytes are parsed or copied. Real Chromium fixture confirms trace appears on retry 1, screenshot/video on failed attempts, and a deleted screenshot is unlinked after regeneration. |
| 2026-09-30 | What is the V2 debug-context boundary? | One pure, deterministic, allow-listed packet contract shared by CLI and offline report; cap JSON at 24 KiB, individual fields at smaller byte limits, redact common credentials/local paths, and never transmit or read attachment contents. | The packet is evidence for user review, not an AI diagnosis. Arbitrary secrets can survive redaction, so preview before sharing is required. Passing-test details remain in the report only when captured evidence exists. |
| 2026-09-30 | How should V3 label failure patterns? | Emit conservative clue IDs only when a matching error and failed step occur on the same attempt; add retry/prior-pass clues only when recorded outcomes support them; otherwise show `unknown`. | Error wording alone can be misleading. Each clue cites evidence IDs in the packet and report, and is presented as an inference rather than a Playwright fact or AI diagnosis. |
| 2026-09-30 | Which new V6 reporter options are justified? | Add no new configuration yet; document and verify the existing Playwright trace option and Logbook capture/redaction limits. | `title`, `redact`, `captureDetails` and size caps already cover the tested debugging workflow. Branding/source-link/debug-cap customization would need concrete usage and a privacy/compatibility design; preserving default schema-v1 output is preferable to speculative options. |
| 2026-09-30 | Should V4–V5 model-provider analysis ship now? | No. Defer provider integration; keep diagnostics local-only. | The user prefers to use the exported debug context manually later and did not authorize hosted transmission. No provider adapter, `analyze` CLI command, API request, or automatic upload is included in this milestone. |
| 2026-10-04 | How should IDE analysis work? | Add an action-only Analyze section and IDE command using VS Code's Language Model API. Model discovery precedes a separate Analyze action; the IDE/provider owns consent, credentials and limits. Include bounded exact-execution evidence and scoped history, stream escaped text, cancel stale selections and keep responses in memory. Custom provider integration and CLI analysis remain deferred. |
| 2026-10-04 | Are HTML embedding and full accessibility review current work? | Remove embedded HTML from the current backlog; defer comprehensive accessibility review. | User said HTML is not required and accessibility can wait. Existing keyboard/theme behavior and checks remain intact. |
| 2026-10-04 | Which analysis workflow should follow the IDE model prototype? | Implement `logbook analyze` as a local agent-task generator first; then hand the shared task to the user's chosen coding-agent chat window for review and submission. | User authorized CLI-first delivery and asked the assistant to choose the workflow. Agent-window handoff preserves the actual agent's workspace tools, model controls and response provenance. The CLI has no fake answer or model execution; its response-length instruction is fulfilled by the agent. Direct provider analysis remains a separate future capability. |
| 2026-10-03 | Which ZIP implementation supports portable run bundles? | Add yauzl/yazl runtime dependencies and their development-only types; bounded lazy reads, deterministic stored entries | Avoid a custom ZIP parser. Validate archive structure, inflated sizes, ratios, paths and SHA-256 payload digests above the archive library. Store entries without compression so highly repetitive logs cannot produce a bundle rejected by its own 100:1 import guard. Fixed ZIP metadata removes host/time variance. Primary APIs: https://github.com/thejoshwolfe/yauzl and https://github.com/thejoshwolfe/yazl. |
| 2026-10-04 | How should the extension hand tasks to installed agents? | Discover contributed chat participants/panels from installed extensions; use an unsent native chat draft where supported, otherwise open the panel and copy the task for explicit pasting/submission. | There is no universal installed-agent draft/response API. Codex's documented add-to-thread commands attach file context rather than accept arbitrary prompt text. Do not guess command argument contracts, auto-submit a query, fabricate agent models, or claim that clipboard contents appeared in a chat composer. Model selection and answers remain in the chosen agent UI; the shared CLI builder requests a concise answer. |
| 2026-10-04 | Does agent-window analysis need a dedicated test-detail section? | Use a compact Analyze with AI split button alongside source actions, a native agent picker and editor notifications. | User approved removing the section because the conversation lives in the agent's window. Remember choices per workspace folder; the main button reuses the choice and the arrow changes it without handing off. Removed agents require a new selection, and model controls remain in the agent UI. |
| 2026-10-04 | Can analysis tasks appear directly in agent inputs? | Replace the copy-only fallback with explicit known input-focus commands and VS Code native webview paste; native chat retains its unsent draft API. | User requires the full prompt and context in chat, with submission left to the user. Installed-agent discovery remains dynamic; verified command contracts determine insertion support. Unknown panel openers cannot establish input focus and report an actionable failure. Never invoke an agent submit command. |

| 2026-10-05 | How should security vulnerabilities and CI audit enforcement be managed? | Add `npm audit --audit-level=moderate` to release workflows and update `vitest` to `^5.0.3`. | Automated security audits in CI block vulnerable release packages.
