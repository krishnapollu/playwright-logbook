# Decisions

| Date | Question | Choice | Reason |
| --- | --- | --- | --- |
| 2026-09-29 | What should T0 contain before implementation tasks? | A minimal buildable ESM scaffold and placeholder reporter | T0 defines layout and verification only; behavior is implemented in later tasks. |
| 2026-09-29 | How should a missing Playwright test ID be derived? | SHA-1 of `project|relative-file|describe-titles|title` | Stable across machines and independent of absolute paths. |
| 2026-09-29 | Did two external-project dry runs complete? | No; keep a human follow-up | Cloned [microsoft/playwright-examples](https://github.com/microsoft/playwright-examples) and [checkly/playwright-examples](https://github.com/checkly/playwright-examples); `npm ci` succeeded in both temporary clones. A Microsoft clock test with a 10-second test timeout and Checkly's local API suite produced no reporter result and were interrupted after roughly 30–45 seconds. In the restricted run, Checkly's server could not bind port 8000 (`EPERM`); an escalated server responded, but the suite still stalled. These attempts do not prove compatibility. |
| 2026-09-29 | Why did the T11 GitHub workflow have no jobs? | Fix matrix expression YAML syntax | GitHub reported “error in your yaml syntax on line 16”; the inline `with: { node-version: ${{ matrix.node }}, cache: npm }` was replaced with a block mapping. |
| 2026-09-29 | Can the release export only ESM? | No; add a CJS reporter entry with esbuild | A fresh tarball installation failed when Playwright resolved the reporter by package name through `require.resolve`: “No exports main defined.” The public ESM entry remains unchanged; `dist/index.cjs` is built for the package `require` condition. esbuild is the one new direct development dependency, used only for this build. |
| 2026-09-30 | How should R0 demo data be generated? | Seeded mulberry32 with fixed UTC run times; write files through the public library APIs | This produces identical shard, run, index, and report bytes across separate output directories while exercising the real merge and rendering pipeline. |
| 2026-09-30 | What version identifies the report v2 release? | Bump the package and `src/version.ts` to `0.2.0`; keep schema version 1 | Report model and capture fields are additive; a minor package bump distinguishes the new report. |
| 2026-09-30 | Should token colors be adjusted for contrast? | Light flaky `#895000`; dark muted `#aab7d4`, accent `#8ba7ff`, failed `#ff777e`, flaky `#ffc06e` | These pairs pass the automated WCAG 4.5:1 test on the surface and relevant tinted backgrounds. |
| 2026-09-30 | Which CI action versions should the e2e job use? | Keep `actions/checkout@v7` and `actions/setup-node@v7` | Both tags are documented in their official GitHub repositories; the e2e job runs on Ubuntu with Playwright Chromium installed. |
| 2026-09-30 | What did the Phase B Playwright probe establish? | `@playwright/test` 1.63.0 supplies `onStepEnd(test, result, step)`, parent-linked steps, output arrays, and failed screenshot path attachments | The isolated details fixture observed `test.step`, `expect`, `pw:api`, `hook`, and `fixture` categories; output entries were strings and the screenshot was `image/png`. Capture uses these verified fields. |
| 2026-09-30 | Which existing tests changed for report v2? | Added assertions to `model.test.ts` and `render.test.ts` for the additive model and template; added optional-capture cases to `schema.test.ts`, `collect.test.ts`, and `reporter.test.ts` | All prior assertions remain; the R7 task card specifically requires coverage in those files. The golden test remains untouched. |
| 2026-09-30 | Should v3 center on aggregating separately invoked suites? | No; refocus v3 on Playwright-native reporting and evidence-grounded AI debugging | Playwright projects and blob-report merging already cover common suite/shard layouts. Separate invocations still need collision safety, but a new group hierarchy is not justified without a concrete Playwright use case. User clarified the product focus. |
| 2026-09-30 | How broad should the real-Playwright fixture be? | Use a bounded behavior matrix with a dedicated UI/API fixture, not every Cartesian product | Installed Playwright 1.63.0 reports `trace` as `application/zip` on retry 1 with `on-first-retry`; failed first attempts supply screenshot (`image/png`), video (`video/webm`) and `error-context` (`text/markdown`). Expected-fail has `expectedStatus: failed`, a failed attempt and `outcome: expected`. Stable outcomes/attachment placement are asserted; binary artifacts and durations are not. See `docs/PLAYWRIGHT-MATRIX.md`. |
| 2026-09-30 | Which Monocart ideas fit v3? | Prioritize trustworthy trace/attachment UX and allow-listed annotations; defer telemetry, coverage and external integrations; reject executable/report-HTML customization | The upstream README describes these features, but Logbook's offline and AI-debugging focus makes evidence quality and explicit consent more valuable than widget parity. See `docs/REPORTER-COMPARISON.md`. |
| 2026-09-30 | How should v3 protect run IDs without breaking explicit re-merge? | Atomically hard-link completed temporary JSON for ordinary shard/run writes; identical replay is a no-op, different content conflicts. Keep `logbook merge` an explicit replacement operation. | The read-only golden test re-merges a previously complete run after removing a shard, so a blanket ban on replacement would break an existing workflow. The reporter's default write path is guarded, never throws or changes Playwright's exit code, and warns on conflict. |
| 2026-09-30 | How should reports handle missing artifacts? | Resolve path availability during reporter/CLI model construction; suppress links for known-missing or escaping files, label unknown links unverified, and identify traces by verified name plus ZIP content type. | `renderReport` stays pure and offline. No trace ZIP bytes are parsed or copied. Real Chromium fixture confirms trace appears on retry 1, screenshot/video on failed attempts, and a deleted screenshot is unlinked after regeneration. |
